## Reproducible defects found

### 1. Trailing unfinished sentence was undercounted

`TextStatistics.fromText` counted only punctuation-terminated boundaries when at least one boundary existed. For text such as:

```text
Hello world! This sentence has no final punctuation
```

it returned one sentence instead of two.

The implementation now counts completed sentence boundaries and adds a remaining non-empty trailing segment. It also recognizes common closing quotation/bracket characters immediately after terminal punctuation.

### 2. Sentence capitalization could split non-BMP letters

`SentenceCapitalizationRule` used `word[0]` and `substring(0, 1)`, which operate on UTF-16 code units. A non-BMP letter can occupy two UTF-16 code units, so a valid Unicode letter at a sentence start could be split and corrupted.

The rule now reads the first Unicode scalar through `runes`, applies case conversion to that scalar, and slices the remaining word after the scalar's UTF-16 width.

### 3. Opening quotes hid valid sentence starts

The capitalization boundary detector handled closing quotes attached to the previous sentence but did not allow opening quotes between sentence-separating whitespace and the next word. Text such as:

```text
Hello world. “next sentence”
```

therefore missed the expected capitalization finding for `next`.

The boundary rule now accepts common opening quote/bracket characters before the next token while preserving the existing requirement for terminal punctuation plus whitespace.

## Features or work still left

No unchecked requirement remains in the committed V2.16 roadmap. The roadmap explicitly treats further work as optional follow-up rather than an unfinished release requirement.

The following are genuine optional directions:

1. Additional built-in language packs beyond English (US) and English (UK).
2. Additional deterministic writing rules or third-party rule/plugin examples.
3. Publication/tag/release automation if the project chooses a first formal GitHub Release convention.
4. Native platform runner scaffolding and native CI/build validation if Android, iOS, Windows, macOS, or Linux are to become repository-supported targets.

The fourth point is important: the committed repository currently contains the shared Flutter/Dart source and the web host. `docs/DEVELOPMENT.md` explicitly instructs contributors to generate additional local platform runners when needed. Native platform support therefore should not be claimed as repository-validated until those runners and corresponding CI/build gates are deliberately added.
